# 处理 `user_already_exists`、邮箱重复与 OTP 串码问题

## 现状与原因

- 当前邮箱本地名前缀主要依赖 `generate_human_like_email_local_part()`，格式为 `名字+姓氏+毫秒时间戳后6位`，实现位于 `core/base_mailbox.py:15`。
- 这个生成策略只有 6 位时间后缀，且在高并发/短时间批量创建时，多个任务可能落在同一毫秒；如果随机名字也碰撞，就会生成相同邮箱。
- 多个邮箱 provider 直接复用这套 local part 逻辑，例如 `GPTMail`、`CF Gmail catch-all`，因此碰撞会跨 provider 出现，见 `core/base_mailbox.py:1824`、`core/cf_gmail_catchall.py:87`。
- `CloudMail` 例外，它当前使用 `1字母+9位字母数字` 的前缀生成方式，碰撞概率较低，见 `core/base_mailbox.py:1253`。
- ChatGPT 注册链路里，`user_already_exists` 当前被视为“可切换到登录态继续”的终态，见 `platforms/chatgpt/refresh_token_registration_engine.py:243` 与 `platforms/chatgpt/refresh_token_registration_engine.py:455`。这能兜底已有账号，但不能避免新注册时邮箱碰撞。
- 你新贴的日志说明不止一个问题：
  - 第一段里先出现 `Failed to register username. Please try again.`，随后整流程重试又拿到了 `wrong_email_otp_code`。
  - 第二段里邮箱验证已经成功进入 `about_you`，但最终 `create_account` 又返回 `user_already_exists`。
- 这说明当前失败链路至少分成两类：
  - `user_already_exists`：更像邮箱地址已被占用/已注册，属于邮箱碰撞或历史账号残留问题。
  - `wrong_email_otp_code`：更像整流程重试后复用了旧邮箱、旧验证码上下文或 IMAP 取到了上一轮验证码，属于 OTP 串码/旧码污染问题。

## 目标

- 降低邮箱本地名前缀碰撞概率，避免新生成邮箱误撞到历史已注册地址。
- 在注册阶段命中 `user_already_exists` 时，优先判定为“邮箱重复”并自动换新邮箱重试，而不是直接走登录补救。
- 避免整流程重试时复用旧验证码或旧邮箱上下文，减少 `wrong_email_otp_code`。
- 保持现有“确实是已存在账号时可登录接续”的兼容能力，避免误伤正常恢复链路。

## 实施方案

### 1. 增强邮箱本地名前缀生成策略

- 修改 `core/base_mailbox.py:15` 的 `generate_human_like_email_local_part()`。
- 保留“human-like”风格，但把后缀改成更高熵组合，推荐：
  - `first + last + 秒级/毫秒级时间片 + 4~6 位安全随机字母数字`
  - 或 `first.last + 8 位 base36 token`
- 关键点：
  - 不再只依赖毫秒时间戳后 6 位。
  - 随机段使用 `secrets`，不要退回 `random`。
  - 输出长度控制在常见邮箱允许范围内，避免过长导致 provider 或站点风控异常。
- 这样所有复用该 helper 的 mailbox provider 都能同步受益，无需逐个 provider 单独修复。

### 2. 给注册引擎补“邮箱重复即换邮箱重试”逻辑

- 在 `platforms/chatgpt/refresh_token_registration_engine.py` 中补一个明确判断函数，例如：
  - `_is_email_already_registered_error(message: str) -> bool`
- 识别关键词至少包含：
  - `user_already_exists`
  - `account already exists`
  - `already exists for this email address`
- 在 `run()` 的注册阶段失败分支里调整策略：
  - 若命中邮箱重复错误，并且当前不是用户显式传入固定邮箱，则直接重新创建邮箱并重跑注册阶段。
  - 若是固定邮箱（用户自己指定），保留当前“走登录恢复”或直接报错的行为，避免擅自替换用户指定邮箱。
- 实现时要限制重试次数，避免死循环；推荐复用现有 `max_retries` 语义或单独增加一个 `chatgpt_email_collision_retries` 配置。

### 2.1 结论：对你这份日志，只能解决后一段，不能单靠现有方案解决前一段

- 对 `create_account -> user_already_exists` 这段，方案能直接命中：
  - 改高熵邮箱名 + 命中错误自动换邮箱重试，能够明显降低并规避这类失败。
- 对 `wrong_email_otp_code` 这段，单改邮箱名还不够，因为它是另一个问题：
  - 整流程重试后如果还沿用同一个 catch-all 邮箱，IMAP 很可能先取到上一轮验证码。
  - 当前邮箱适配器只按“已使用 code 值”去排除，不一定按“本轮发送时间之后的新邮件”严格筛选。
  - 如果上一轮验证码未被标记为 used，或新旧轮次都发到了同一邮箱，就可能把旧 OTP 拿去验证新会话，触发 `wrong_email_otp_code`。

### 3. 给整流程重试补“邮箱与 OTP 隔离”逻辑

- `AccessTokenOnlyRegistrationEngine` 仍保留整流程重试，见 `platforms/chatgpt/access_token_only_registration_engine.py:106`；你的日志中的“整流程重试 3/3”就是这条链路触发的。
- 这条链路需要额外修复，不然即使邮箱生成概率变低，仍可能在重试时出现旧 OTP 串入。
- 建议同时做 3 件事：
  - 每次整流程重试都强制重新创建邮箱，不复用上一轮邮箱地址。
  - 收码时优先按 `otp_sent_at` 过滤，只接受发送验证码之后到达的新邮件。
  - 在邮箱适配器内维护“本轮 attempt id / 当前邮箱地址”的隔离，切换邮箱后清空上一轮 `_used_codes` 与旧 before_ids。

### 4. 收码层按时间和邮箱上下文做强过滤

- 你的 `CFGmailCatchAll` 是 catch-all + Gmail IMAP，本质上同一个 Gmail 收件箱会承接多个别名地址；如果只扫 INBOX 而不过滤轮次，很容易串码。
- 现有 `wait_for_code()` 虽然支持 `otp_sent_at` 参数，但 `core/cf_gmail_catchall.py:174` 的实现里并未基于该时间做消息过滤。
- 建议在 `CFGmailCatchAllMailbox.wait_for_code()` 里补两层过滤：
  - `To` / 正文里必须匹配当前 alias 邮箱地址；
  - 邮件时间必须晚于 `otp_sent_at`（允许少量时钟偏差，例如 -10s 容忍）。
- 如果 IMAP 取到多封候选邮件，只返回最新且满足时间窗口的那一封里的验证码。

### 5. 注册状态机补“用户名注册失败”的专门策略

- `Failed to register username. Please try again.` 出现在 `register_user()` 阶段，早于 OTP 校验完成。
- 这类错误很可能是注册密码页提交时的瞬时冲突、风控或用户名资源占用，不一定是邮箱重复。
- 建议把它从笼统“HTTP 400”里拆出来：
  - 若命中 `Failed to register username`，优先判定为“本轮注册上下文不可继续”，直接丢弃当前邮箱与 session，换新邮箱开新轮次。
  - 不要在同一邮箱上继续整流程重试，否则后续容易把上一轮 OTP 混入下一轮。

### 6. 区分“重复邮箱重试”与“已有账号恢复登录”

- 当前 `_should_switch_to_login_after_register_failure()` 把 `user_already_exists` 直接归类为登录恢复条件，这会掩盖邮箱生成碰撞问题。
- 调整为两层判断：
  - 第一层：是否邮箱重复 -> 优先换邮箱重试。
  - 第二层：若不换邮箱（固定邮箱/超出重试上限）-> 再决定是否切到 OAuth 登录恢复。
- 这样既能解决邮箱生成重复，也不破坏已有账户恢复场景。

### 7. 兼容现有邮箱服务适配器行为

- `platforms/chatgpt/plugin.py:83` 的 `GenericEmailService.create_email()` 每次调用都会向 mailbox 申请新地址；只要注册引擎在重试时再次调用 `_create_email()`，即可自然拿到新邮箱。
- 需要确认/修正一个边界：
  - 当 `email` 是外部传入固定值时，不应自动替换。
  - 当 `self.mailbox` 自生成邮箱时，允许自动替换。
- 这一点实现时应以 `fixed_email` 或等价变量为准做保护。
- 还需要补一个行为约束：
  - 当邮箱地址发生切换时，邮箱适配器内部的 `_used_codes`、最近成功验证码缓存、`before_ids` 都应视为失效并重建。

### 8. 补测试覆盖

- 更新/新增 `tests/test_chatgpt_register.py` 用例：
  - `user_already_exists` + 非固定邮箱：第一次注册失败，第二次自动创建新邮箱并成功。
  - `user_already_exists` + 固定邮箱：不更换邮箱，维持登录恢复或报错路径。
  - 校验第二次 `register_complete_flow()` 收到的新邮箱与第一次不同。
- 更新/新增整流程重试测试：
  - 第一次出现 `Failed to register username`，第二次必须重新创建邮箱，而不是沿用第一次邮箱。
  - 第一次邮箱收到旧 OTP，第二次邮箱/第二轮时间窗只允许读取新 OTP，避免 `wrong_email_otp_code`。
- 补 helper 单测（可放在现有 mailbox 测试文件或新增测试文件）：
  - 连续多次调用 `generate_human_like_email_local_part()`，断言无重复且格式合法。
- 补 `CFGmailCatchAll` 测试：
  - 同一收件箱里存在旧邮件和新邮件时，只提取 `otp_sent_at` 之后、且目标 alias 匹配的验证码。
- 如需最小化改动，也可以只在注册测试里 mock 轮换邮箱，验证引擎分支逻辑。

## 验证方式

- 运行与注册引擎相关测试，至少覆盖：
  - `tests/test_chatgpt_register.py`
- 如项目有更细的 mailbox 测试，再补跑对应测试文件。

  - 明确丢弃旧邮箱/旧会话
  - 第二次创建全新邮箱

## 风险与注意点

- 如果某些 provider 对 local part 长度/字符有隐藏限制，需要控制后缀长度，只使用小写字母数字。
- 如果 `user_already_exists` 在某些场景下确实表示“该用户原本就应该登录”，过于激进地重试会浪费一次注册机会；因此必须保留固定邮箱与重试上限保护。
- 修改后应避免影响依赖“邮箱看起来像真人命名”的外部逻辑，因此建议继续保留名字词典，只提升后缀熵。
- `CFGmailCatchAll` 依赖 IMAP 时间与头部字段，实际邮件头格式可能不完全一致；实现时需要保留兜底逻辑，避免因为过滤过严导致收不到码。

## 推荐落地顺序

1. 先改邮箱 local part 生成函数，降低根因碰撞概率。
2. 再改 `refresh_token_registration_engine`，把 `user_already_exists` 优先视为“可换邮箱重试”的错误。
3. 再改 `CFGmailCatchAll` 与 `access_token_only_registration_engine`，解决整流程重试时的旧 OTP 串码。
4. 最后补测试并跑相关测试，确认邮箱切换、OTP 过滤、固定邮箱分支都正常。
